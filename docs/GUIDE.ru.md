## Первый запуск

1. Вкладка **«Серверы»**: вставьте адрес подписки или ссылку на сервер в пустой источник `src1`.
   Тип источника определяется по тексту.
2. Нажмите **«Сохранить и применить»**. Правило `main` (списки сообщества Russia inside, Discord и
   Telegram) уже берёт серверы из `src1`.
3. Откройте **«Дашборд»**. Плитка сервера, через который идёт правило, выделена.

Пока ни один источник не заполнен, podkop ничего на роутере не меняет.

## Серверы

Источник — это одно из:

- **подписка** — адрес провайдера. **«Загрузить»** показывает её серверы ещё до сохранения. После
  «Сохранить и применить» роутер сам скачивает список и хранит его, так что правила работают и при
  старте без сети. В окне подписки — её состояние, трафик и срок от провайдера, кнопка
  **«Обновить сейчас»** и кнопки для копирования ссылок;
- одна или несколько **ссылок на серверы** (`vless://`, `ss://`, `trojan://`, `hy2://` …; см.
  [примеры](../String-example.md));
- **Outbound JSON** для sing-box;
- **интерфейс** — туннель, настроенный на роутере (WireGuard, AmneziaWG …), модем или второй WAN.

**User-Agent** и **«Дополнительные заголовки»** подписки: некоторые провайдеры отдают список только
названным ими приложениям, а podkop получает веб-страницу или заметки вроде «откройте ссылку в
приложении». Впишите в User-Agent одно название приложения, без версии (например, `INCY`), и
нажмите **«Загрузить»**: окно скажет, если на это название провайдер присылает JSON или YAML,
которые podkop пока не читает, веб-страницу или заметки, а список, который уже используется,
остаётся. Роутер по-прежнему отправляет свой идентификатор устройства (HWID) и занимает своё место
среди устройств подписки: HWID и другие заголовки устройства, адрес клиента (`X-Forwarded-For` …) и
заголовки самого соединения задать нельзя. Дополнительные заголовки (`Имя: значение`, по одному в
строке) нужны для ключа, который требует провайдер: глобальная проверка показывает только их имена,
и уходят они только на хост адреса подписки, а не на другой хост, куда он перенаправит. User-Agent —
название приложения, а не секрет: глобальная проверка его показывает.

Порядок источников (перетаскивание ☰) меняет только вид. Отметка **«Не использовать для загрузки
списков и подписок»** исключает источник из загрузок. Она нужна, например, для подписки с малым
трафиком или туннеля в закрытую сеть.

## Правила

Правило говорит, какие сайты через какие серверы идут. Если сайт есть в нескольких правилах,
действует верхнее; порядок меняется перетаскиванием ☰. У правила четыре вкладки:

- **«Основное»** — списки правила. Это могут быть списки сообщества, свои домены и подсети
  (**«Динамический список»** или **«Текстовый список»**), списки по ссылке и **«Полностью маршрутизированные IP-адреса»** —
  устройства, весь трафик IPv4 которых идёт по этому правилу. Подсети могут быть IPv6 (см.
  [IPv6](#ipv6)); устройства, направляемые целиком, задаются адресами IPv4.
  **«Только для устройств»** ограничивает правило частью устройств: см. [Правило для части устройств](#правило-для-части-устройств).
- **«Серверы»** — одна или несколько строк. Строка — это источник и, по желанию, фильтры.
  **«Имя содержит»** и **«Имя не содержит»** ищут начало слова: `NL` найдёт `NL-1` и
  `Amsterdam NL`, но не `RU2NL`. Столбец **«Через»** подключает к серверам строки через другой
  источник. Строкой может быть также **«Напрямую»** (исключение) или **«Блокировать»**.
- **«Запасные»** — строки по порядку. Они берутся, когда не отвечает ни один сервер правила. Если
  запасной — «Блокировать», правило возвращается на свои серверы вскоре после того, как сеть
  вернулась.
- **«Доп. настройки»** — выбор сервера и смешанный прокси правила (SOCKS5 и HTTP на порту
  роутера, см. [Смешанный прокси](#смешанный-прокси)).

Выбор сервера:

| Режим | Как выбирается сервер | Цена |
|---|---|---|
| Самый быстрый | наименьшая медиана задержки по проверкам серверов; переключение — только на сервер, который быстрее на допуск (в «Настройках») | только проверки |
| Самый быстрый с учётом потерь | задержка с учётом потерь, которые насчитывают скачивания по 256 КБ через текущий сервер и три следующих лучших | около 50 МБ в сутки на правило при 30 минутах по умолчанию |
| Балансировка между лучшими | устройства распределяются между лучшими серверами и остаются на своём; сервер с большими потерями устройств не получает | около 60 МБ в сутки на правило (проверяются пять серверов) |

### Правило для части устройств

Поле **«Только для устройств»** (вкладка «Основное») ограничивает правило перечисленными
устройствами — адресами и подсетями IPv4 или IPv6: правило берёт их трафик, и ничей больше.
Остальные устройства этим правилом не берутся: они идут дальше, к правилам ниже, а если ни одно их
не берёт — напрямую.

Пример: YouTube через серверы только на телевизоре, на остальных устройствах заблокирован.

1. Правило «Телевизор»: список сообщества YouTube, **«Только для устройств»** — адрес телевизора,
   ваши серверы.
2. Ниже — правило «Без YouTube»: список сообщества YouTube, строка серверов **«Блокировать»**.

Порядок важен: правило выше, которое берёт тот же список для всех устройств, возьмёт и телевизор.
Столбец «Списки» таблицы правил скажет об этом в строке правила «Телевизор» («… уже есть в
правиле «…» выше»). При правильном порядке в строке правила «Без YouTube» будет «… есть в правиле
«…» выше, но только для его устройств»: так и должно быть, остальные устройства до него доходят.

- Поле смотрит на адрес: устройство, которое заняло чужой адрес, для правила и есть то устройство.
  Это не замок.
- Сначала закрепите за устройством постоянный адрес — статическую аренду (статический адрес DHCP):
  с новым адресом для правила это другое устройство. Телефон или ноутбук с частным (меняющимся)
  адресом Wi-Fi получает новый MAC-адрес, а с ним и новую аренду: отключите это на устройстве для
  своей сети.
- Ответы DNS одинаковы для всех устройств: DNS роутера их не различает. Остальные устройства тоже
  получают адреса FakeIP для имён из списков и не получают для них адресов IPv6 (при **«IPv4 и
  IPv6»** в ответах DNS они теряют IPv6 для этих имён). podkop отправляет их соединения напрямую
  через sing-box, который открывает их заново с роутера: такие соединения не ускоряются
  (offloading), **«Отключить QUIC»** действует на них для этих имён, а правила файрвола для
  отдельных устройств (ограничения по времени), правила pbr или mwan3 по адресу источника, SQM по
  IP и nlbwmon больше не видят их как трафик этого устройства.
- **«Полностью маршрутизированные IP-адреса»** такого правила должны быть среди его устройств;
  другие страница не примет. «Полностью маршрутизированные IP-адреса» всех правил и
  **«Исключённые из маршрутизации IP-адреса»** действуют раньше него: устройство, которое целиком
  направляет другое правило или которое исключено, это правило не берёт (таблица об этом скажет).
  Иначе с правилами наверху, у которых все строки серверов — только **«Напрямую»** или только
  **«Блокировать»**, выше всех остальных включённых правил: они действуют первыми, и такое правило
  берёт свои устройства для своих списков, даже если их целиком направляет другое правило или они
  исключены.
- IPv6: адреса IPv6 устройства меняются (временные адреса), поэтому адрес IPv6 в поле работает,
  только если он постоянный. Это важно лишь при **«Трафик IPv6: Через podkop»** и подсетях IPv6 в
  списках; имена из списков всегда идут по IPv4. С уникального локального адреса (`fd…`) устройство
  выходит в интернет, только если у него нет глобального адреса IPv6 и роутер транслирует его IPv6
  (NAT66); с локального адреса канала (`fe80::…`) — никогда, и страница его не примет.
- Смешанный прокси правила остаётся открытым для всех устройств сети. Режимы BitTorrent поле не
  видят (см. [BitTorrent](#bittorrent)).
- Трафик самого роутера обычно не берётся: его источник — адрес WAN роутера. Он берётся, если этот
  адрес среди устройств: роутер стоит за другим роутером, и его адрес WAN лежит в подсети из поля;
  для IPv6 роутер, у WAN которого нет своего адреса IPv6, отправляет трафик со своего адреса в
  локальной сети, а его содержит подсеть локальной сети (`/64`) из поля.
- Изменение поля перезапускает sing-box, как и изменение списков правила: открытые соединения
  обрываются.
- Более старая версия podkop поле не знает: правило в ней берёт все устройства.
- Какие правила берут устройство, на котором страницу не открыть (телевизор), покажет
  `podkop device 192.168.1.50` на роутере — по порядку. Глобальная проверка называет устройства
  каждого такого правила (адреса IPv4; адреса IPv6 только считаются), а в разделе **«This device»**
  говорит, есть ли среди них адрес IPv4 устройства, на котором её запустили.

### Смешанный прокси

Правило может открыть прокси на роутере: SOCKS5 и HTTP на одном порту адреса LAN
(**«Доп. настройки» → «Включить смешанный прокси»**). Всё, что приложение отправит туда, идёт
через серверы правила.

**Имя и пароль.** Без них прокси может пользоваться любое устройство, которому доступен порт, в
том числе программа на устройстве вашей сети. Если заданы оба, приложение должно войти: по
SOCKS5 — с именем и паролем, по HTTP — с Basic-аутентификацией. У SOCKS4 пароля нет, и тогда он
не принимается. Кнопка **«Создать»** подставит случайный пароль из 16 букв и цифр (и имя
`podkop`, если имени нет); пароль, набранный вручную, — не короче 8 символов. Оба поля пусты —
прокси без логина, как до 0.8.21.

- Логин передаётся без шифрования, как и трафик приложения до роутера. Он закрывает порт от
  чужих и от программ вашей сети, но не делает безопасным порт, проброшенный из интернета. Чтобы
  пользоваться прокси снаружи, подключайтесь к роутеру через VPN (WireGuard).
- В адресе прокси логин пишется так: `socks5h://имя:пароль@192.168.1.1:2080` или
  `http://имя:пароль@192.168.1.1:2080`. Знак пароля, кроме букв, цифр и `-._~`, пишется как `%`
  и его код (`@` — это `%40`); в созданных паролях таких знаков нет.
- У браузеров нет полей для логина SOCKS5 (Chrome не умеет его вовсе): укажите браузеру
  HTTP-прокси с тем же адресом и портом — он спросит имя и пароль.
- Пока прокси выключен, логин остаётся в настройках. Глобальная проверка, `show_config` и
  `show_sing_box_config` его скрывают; глобальная проверка говорит о каждом прокси, слушает ли он
  порт и спрашивает ли логин.
- Неверный пароль, набранный в приложении, sing-box пишет как есть в системный журнал
  (`logread`) и в журнал YACD; в журнале podkop (**«Посмотреть логи»**, `podkop check_logs`) он
  скрыт.

## Настройки

Вкладка — один список; здесь поля сгруппированы по смыслу.

| Поля | Что задают |
|---|---|
| DNS-серверы | строки DoH, DoT, UDP или **«DNS провайдера»**, которые спрашиваются **«По порядку»** или **«Сначала самый быстрый»** (сервер IPv6 — как `[2001:4860:4860::8888]:853`); bootstrap DNS-сервер; TTL в ответах podkop |
| Адреса в ответах DNS | для имён вне списков: **«Предпочитать IPv4»** (адрес IPv6 только для имени без IPv4), **«Только IPv4»** или **«IPv4 и IPv6»**. См. [IPv6](#ipv6) |
| Трафик IPv6 | **«Мимо podkop»** или **«Через podkop»**. См. [IPv6](#ipv6) |
| Проверка серверов | адреса, интервал и допуск проверок задержки для всех правил; проверка загрузки |
| uTLS-fallback | включено по умолчанию: сначала пробуется отпечаток ссылки без ключа X25519MLKEM768, затем firefox, затем отпечаток как есть; первый прошедший запоминается для сервера и раз в сутки проверяется заново |
| BitTorrent | **«Как остальной трафик»**, **«Мимо podkop»**, **«Блокировать»** или **«Через серверы правила»**; два последних — для того, что берёт podkop, или для всей сети. См. [BitTorrent](#bittorrent) |
| Открытые списки масок | откуда «Подобрать маску» берёт имена сайтов из белых списков |
| Интерфейсы | интерфейс локальной сети, который обслуживает podkop, и выходной интерфейс для его собственных соединений |
| YACD | панель YACD: включена или нет, с каких интерфейсов открывается, её ключ |
| Прочее | «Отключить QUIC», частота обновления списков, «Dont Touch My DHCP!», файл кэша, уровень журнала, «Исключить NTP», IP-адреса, исключённые из маршрутизации |

## BitTorrent

«Настройки» → **BitTorrent** — что делать с трафиком торрент-клиентов.

| Режим | Что делает |
|---|---|
| Как остальной трафик | ничего особенного: решают правила, как для любой программы |
| Мимо podkop | торренты идут напрямую в интернет, а не через ваши серверы (исключения — ниже); роутер может ускорять их (flow offloading) |
| Блокировать | отбрасывается |
| Через серверы правила | уходит на серверы выбранного правила, например без лимита трафика |

**«Блокировать»** и **«Через серверы правила»** действуют на то, что берёт podkop (устройства,
направленные целиком, и адреса из списков), или на **всю сеть**.

Клиент распознаётся по первым пакетам DHT, uTP и трекеров, по рукопожатию BitTorrent, по пирам,
которых назвали трекер или DHT, а зашифрованное соединение — по форме его рукопожатия.

Ещё два поля:

- **«Искать клиенты, которые прячутся»** (для всей сети, по умолчанию выключено). Клиент,
  настроенный без DHT, uTP и обмена пирами, с обязательным шифрованием, не даёт роутеру ни одного
  признака. С этой настройкой у устройства, которое разом открывает соединения ко многим новым
  адресам на необычных портах, новые соединения проверяются. Когда три из них оказываются
  BitTorrent, считается, что на устройстве работает клиент, а соединения, открытые им раньше,
  закрываются.
  Проверяемые соединения идут через sing-box и не ускоряются (flow offloading).
- **«Торрент-клиенты на самом роутере»**. Детектор видит устройства сети, а не программы самого
  роутера. Укажите пользователя, от имени которого работает клиент (`transmission` и `aria2` в
  пакетах OpenWrt), и весь трафик этого пользователя пойдёт по выбранному режиму. Клиенту с
  поддержкой SOCKS5 (qBittorrent, Deluge) можно вместо этого указать
  [смешанный прокси](#смешанный-прокси) правила — с его именем и паролем, если у прокси есть
  логин (в qBittorrent — «Аутентификация», в Deluge — тип «Socks5 Auth»): всё, что он туда
  отправит, пойдёт через серверы этого правила, каким бы ни был режим BitTorrent. У Transmission
  и aria2 настройки прокси для пиров нет.

Чего это не умеет:

- **IPv6** не просматривается.
- **Клиент, который не подключается заново.** Зашифрованное соединение распознаётся, только когда
  оно уже открыто; podkop закрывает его, чтобы клиент открыл его снова — уже правильным путём.
  rTorrent и aria2 с обязательным шифрованием делают это редко: при «Мимо podkop» и «Через серверы
  правила» такие соединения остаются на прежнем пути — для пиров, которых не назвал ни один ответ
  трекера или DHT.
- **Небольшая раздача** у клиента, который прячется, во всей сети не находится: должны
  состояться три зашифрованных рукопожатия, а большинство адресов из ответа трекера не отвечает.
  В наших тестах ответа трекера с 50 пирами хватало, с 20 и меньше — нет.
- **Клиент, который прячется, с открытым портом** (проброс порта, UPnP): то, что он открывает
  сам, блокируется, а соединения, которые пиры открывают к нему снаружи, — нет.
- **Похожие программы.** Роутер I2P принимается за BitTorrent. Прокси-клиент, чьи соединения с
  первого байта выглядят случайными (shadowsocks-rust, VMess в V2Ray), принимается за
  торрент-клиент, если держит соединения с тремя и более серверами на необычных портах; на
  устройстве, где работает и торрент-клиент, достаточно одного такого соединения.
- **Flow offloading.** Соединение, которое роутер ускорил, не проходит ни одного правила. Где
  возможно, podkop решает по первому пакету. Во всей сети клиент, чей единственный признак лежит
  в данных TCP-соединения (трекер по обычному HTTP, открытое рукопожатие), при включённом
  offloading не распознаётся, если его не поймает «Искать клиенты, которые прячутся». Эта
  настройка проверена только с программным offloading — с аппаратным и на реальных роутерах пока
  нет.
- **Клиент на роутере, запущенный от root**, и программы за интерфейсом, который не выбран в поле
  «Сетевой интерфейс источника», не видны. При «Блокировать» веб-интерфейс клиента на роутере
  отвечает только частным адресам локальной сети.
- **Первый анонс** на HTTP-трекер из ваших списков и каждый анонс на HTTPS-трекер идут по
  правилам, как на любой сайт.
- **«Только для устройств»** правила режимы не видят: **«Блокировать»** и **«Через серверы
  правила»** действуют на адреса списков для всех устройств.

## IPv6

Имена из списков podkop в любом режиме получают адреса FakeIP IPv4: устройство идёт к такому
сайту по IPv4 через сервер правила, а сервер сам разрешает имя — в IPv4 или IPv6. Настройки меняют
остальное:

- **«Адреса в ответах DNS»** — что получают устройства и роутер для имён вне списков. При
  **«IPv4 и IPv6»** устройство с IPv6 обычно выбирает для таких сайтов IPv6; они идут мимо podkop,
  как и их IPv4.
- **«Трафик IPv6» — «Через podkop»** отправляет IPv6 к подсетям IPv6 из списков (у Telegram,
  например, есть дата-центры в IPv6; приложение может подключаться к ним, не спрашивая DNS) по их
  правилам, как IPv4. Серверам такого правила нужен IPv6: сервер без него эти соединения не
  установит, и это видно в журнале podkop. **«Мимо podkop»** оставляет IPv6 в покое, как до 0.8.20.

Чего это не делает: устройства, направляемые целиком («Полностью маршрутизированные IP-адреса»),
направляются только по IPv4; настройка BitTorrent смотрит только IPv4; у FakeIP нет адресов IPv6,
поэтому устройство только с IPv6 не получит адреса для имени из списка. Роутер, которому провайдер
даёт IPv6 в режиме relay, передаёт устройствам DNS-сервер провайдера: они спрашивают его, а не
podkop, и глобальная проверка об этом предупреждает (раздайте им DNS-сервер роутера в настройках
DHCP локальной сети).

## Дашборд

- Плитка сервера, через который идёт правило, выделена. Если серверов несколько, строка под
  именем правила ещё и говорит, как он выбран: автовыбор, запасной или **«Вручную»**. Серверы
  показаны плитками, по ярусам: самый быстрый, затем запасной 1,
  запасной 2 …
- На плитке — задержка. В режимах с потерями ещё и потери (`~`, пока проверок мало) и число
  устройств в балансировке (`⇄N`).
- Нажатие на плитку закрепляет этот сервер. **«Вернуть автовыбор»** снимает закрепление.
  **«Тестирование задержки»** проверяет серверы сейчас и показывает результат рядом с медианой.
  Для правила с несколькими серверами это раунд проверки серверов, такой же, как собственные раунды
  правила (каждый сервер — ссылкой раунда, а если она не ответила — следующей), и результат — новая
  медиана. У правила с одним сервером он проверяется отдельно: первой ссылкой проверки серверов, а
  если она не ответила — следующей.
- У неработающего сервера появляется метка с причиной: нет ответа, заморозка, лимит, нет пути,
  отказ и другие. **«Проверить»** (или **«Проверить проблемные»**) проверяет сервер и называет вид
  блокировки. Окно может предложить **«Обход блокировки для этого сервера»**:

  | Вердикт | Обход |
  |---|---|
  | лимит (соединения обрываются около 16–20 КБ) | маска: сначала уходит поддельное TLS-приветствие сайта из белого списка. **«Подобрать маску»** ищет имя, которое работает на этом сервере |
  | заморозка | TLS-приветствие разбивается на две записи, или автосмена отпечатка uTLS |
  | нет пути | подключение через тот сервер, через который проверка до него достучалась |

  Обход принадлежит серверу и переживает переименование. Пометка на плитке открывает окно, где
  обход можно убрать.
- Карточка **BitTorrent** (если BitTorrent не «Как остальной трафик») показывает трафик
  BitTorrent-клиентов: по видам (DHT и трекеры, uTP, TCP, входящие) и по путям — сколько
  устройства отправили и получили, число соединений и итог. Роутер считает IPv4 вместе с
  заголовками пакетов, поэтому числа немного больше, чем у самого клиента. Входящие соединения
  (проброс порта) учитываются, если клиент слушает тот же порт, что и его DHT или uTP. При
  аппаратном offloading на чипе, который не сообщает байты по соединениям, у ускоренных
  соединений могут быть учтены только первые пакеты. **«Сбросить»** начинает счёт заново, без
  перезапуска podkop.

## Диагностика

- **«Запустить диагностику»** проверяет DNS, sing-box, правила файрвола, FakeIP и серверы, через
  которые правила идут сейчас, — каждый первой ссылкой проверки серверов, а если она не ответила —
  следующей. Без прокси она запрашивает сразу все ссылки проверки серверов и показывает их
  медиану; не ответившая ссылка названа (её может блокировать провайдер). Глобальная проверка
  делает то же.
- **«Получить глобальную проверку»** собирает всё в один отчёт, ключи и пароли в нём скрыты. Этот
  отчёт и нужно прикладывать к issue. Адреса локальной сети не скрываются: в настройках в отчёте
  видны устройства правил, в том числе адреса IPv6.
- **«Посмотреть логи»** и **«Показать sing-box конфигурацию»** показывают журнал и работающую
  конфигурацию.
- Перезапуск, остановка, запуск, автозапуск — вкл. и выкл.

## Если что-то не работает

1. «Диагностика» → **«Запустить диагностику»**. Строка с ошибкой говорит, что не так.
2. **«Получить глобальную проверку»**. Она смотрит ещё часы роутера, работает ли dnsmasq с
   записанными для него настройками, выбор сервера и BitTorrent.
3. Сервер помечен на дашборде: **«Проверить»**, затем предложенный обход.
4. Не приходит подписка: её окно показывает, какие пути пробовались и почему каждый не сработал.
   Для списков `podkop list_status` показывает последнюю ошибку каждого.
5. Правило для части устройств не берёт устройство: `podkop device <его адрес>` на роутере
   перечислит по порядку правила, которые его берут; на самом устройстве раздел **«This device»**
   глобальной проверки скажет, есть ли его адрес IPv4 среди устройств правила.
6. Всё ещё не работает: откройте [issue](https://github.com/podkop-net/podkop-experimental/issues)
   с глобальной проверкой и описанием того, что вы делали. Журнал — `logread -e podkop`.
7. BitTorrent идёт не тем путём: запустите `podkop bittorrent_record 10 --reset`, начните загрузку
   и через 10 минут приложите файл, который команда назовёт. В нём только числа: ни адресов, ни имён.

## Обновление

Запустите команду установки из [README](../README.ru.md#установка) ещё раз. Она показывает, какой
выпуск поставит и какая версия стоит сейчас, и говорит, если делать нечего. Затем очистите кэш
браузера, прежде чем открыть страницу (или откройте её в приватном окне): браузер может держать
страницу прежнего выпуска.

- `--release 0.8.19` в конце команды ставит этот выпуск, в том числе более старый (0.8.8 или
  новее). Настройки остаются в формате podkop-exp; более старый выпуск не знает параметров,
  добавленных после него.
- Если GitHub отказывает («GitHub refused the request»: его API принимает 60 запросов в час с одного
  адреса), скачайте пакеты на компьютере и используйте `--from`, как
  [сказано](../README.ru.md#установка-без-api-github) в README.

## Командная строка

| Команда | Что делает |
|---|---|
| `podkop global_check` | глобальная проверка |
| `podkop check_logs` | журнал бэкенда и sing-box |
| `podkop show_config`, `podkop show_sing_box_config` | настройки и работающая конфигурация sing-box, секреты скрыты |
| `podkop reload` | применить настройки заново и сказать, чем кончилось |
| `podkop device <адрес>` | правила, которые берут трафик устройства с этим адресом, по порядку |
| `podkop list_update` | скачать все списки сейчас |
| `podkop subscription_update [имя]` | скачать подписку (или все) сейчас |
| `podkop bittorrent_stats` | статистика BitTorrent в JSON |
| `podkop bittorrent_reset` | начать статистику BitTorrent заново |
| `podkop bittorrent_record [минуты] [--reset]` | отчёт о BitTorrent для проверки: снимок раз в 10 с (по умолчанию 10 минут), без адресов |
| `service podkop restart` | перезапустить службу |

`podkop` без аргументов перечисляет все команды.
